# `scripts/` — database schema reference

`init_db.sql` is the single DDL file that builds the whole ALCheMy
PostgreSQL schema (it only runs automatically the first time the
`postgres_data` volume is created — see the root `CLAUDE.md` for how to
apply later changes to an existing database). This file is the human-readable
companion to it: one section per table, in plain language, generated by
cross-checking `information_schema.columns` against the live `data_dictionary`
table on 2026-08-25 (121/121 ALCheMy columns documented; `job_leads` is a
separate, unrelated personal project sharing this same Postgres instance and
is intentionally out of scope here).

If a query ever needs the dictionary as *data* rather than prose — for a UI
tooltip, or for the RAG agent to introspect the schema — read the
`data_dictionary` table directly; it is kept in sync with the real columns by
`init_db.sql` itself, not by hand-copying into this file.

---

## How the tables relate

```
synthesis_experiments (parent, 1 row per synthesis)
        ▲ sample_code
        │
characterization_measurements (child, 1 row per instrument measurement)


rag_documents (parent, 1 row per source file: paper, notebook, protocol...)
        ▲ document_id
        │
rag_chunks (child, 1 row per ~1200-character fragment + its embedding)


authorized_researchers ──▶ audit_log            (1 row per tool call)
                       └─▶ agent_chat_log        (1 row per question+answer)

data_dictionary   -- documents every column of every table above
```

Two independent parent/child pairs, plus a governance layer that watches
both. Nothing in the RAG tables references `synthesis_experiments` — they are
deliberately separate: the chat agent can be given access to one without the
other.

## 1. `synthesis_experiments` — the lab notebook, digitised

**What it is**: one row per MOF/POP synthesis batch. The parent table of the
whole platform; `sample_code` (e.g. `RS1`, `RS102`) is its primary key and is
what every other characterization measurement hangs off of.

**Filled by**: `notebooks/01_Excel_Ingestion_and_Transformation.ipynb`, which
reads the master Excel file and UPSERTs into this table (`ON CONFLICT
(sample_code) DO UPDATE`) — deliberately an UPSERT, not an INSERT, so it can
never delete rows that n8n or the characterization lane wrote.

**Columns**, grouped by the `section_name` used in `data_dictionary`:

| Section | Columns | What it captures |
|---|---|---|
| GENERAL INFORMATION | `sample_code`, `synthesis_date`, `synthesis_type`, `researcher_name`, `research_unit`, `hts_number`, `well_position`, `metal_center`, `metal_source`, `linker`, `file_hash_md5`, `measurement_status`, `created_at`, `updated_at` | Who/when/what, plus the MD5 **business natural key** (over `sample_code` + `synthesis_date` + `researcher_name` + `research_unit` + `metal_center` + `linker`) that gates the Excel ingestion against duplicates |
| THEORETICAL DESIGN | `metal_conc_m`, `lm_ratio`, `metal_mass_mg`, `linker_mass_mg`, `secondary_linker_mg`, `reactor_volume_ml` | The intended recipe before weighing anything |
| SOLVENTS | `h2o_pure_ml`, `h2o_total_ml`, `meoh_ml`, `etoh_ml`, `proh_1_ml`, `dmf_ml`, `def_ml`, `total_volume_ml` | Every solvent volume, plus the homogenised total |
| THERMAL RAMP | `temp_initial_c`, `heating_time_hours`, `heating_rate_c_min`, `temp_target_c`, `time_hours`, `cooling_time_hours`, `cooling_rate_c_min`, `temp_final_c` | The heating profile, parsed from free-text ramp descriptions in the Excel |
| MODULATORS & ADDITIVES | `hcl_active_mmol`, `hf_active_mmol`, `koh_active_mmol`, `formic_acid_mmol`, `acetic_acid_mmol`, `propionic_acid_mmol`, `tfa_mmol`, `cf3so3h_mmol`, `triethylamine_mmol`, `meo3s_mmol` | Modulator chemistry, always in **millimoles of active substance**, not µL of stock solution — the notebook does that stoichiometric conversion on ingestion |

**Known gap** (see root `CLAUDE.md`): the DDL has a "Section 6: Experimental
Weighings & Yield" header comment but never creates those columns
(`exp_metal_mass_mg`, `mof_exp_mass_mg`, `yield_percent`, etc.) — the
Streamlit verification flow currently writes them to CSV/Excel only, not to
this table.

## 2. `characterization_measurements` — one row per instrument file

**What it is**: the child of `synthesis_experiments` (`sample_code`, `ON
DELETE CASCADE`). One row per raw instrument file, whatever the technique.

**Filled by**: the n8n ingestion webhook (live pipeline) and
`src/ingest_datalake_to_postgres.py` (historical backfill) — both route
through the same parser contract described in `src/README.md`.

| Column | Type | What it means |
|---|---|---|
| `measurement_id` | UUID, PK | Row identity |
| `sample_code` | FK → `synthesis_experiments` | Which synthesis this measurement belongs to |
| `researcher_name` | text | Researcher responsible for the *sample* |
| `researcher_email` | text | Person who *submitted* the file through the n8n portal — must be in `authorized_researchers` |
| `technique` | text | `PXRD`, `VT-XRD`, `TGA`, `FTIR`, `ADSORPTION`, `UV_VIS`, `SEM`, `ICP`, `EA` |
| `operator_name` | text | Who physically ran the instrument (ISO 17025 traceability) |
| `measurement_tag` | text | Free label distinguishing repeats of the same sample (`as_synthesized`, `activated_150C`, ...) |
| `instrument_name` | text | Equipment model |
| `file_name`, `raw_file_path` | text | Original file name and its path inside the data lake (container path, not host path) |
| `data_json` | JSONB, GIN indexed | Parser output — always `{header_metadata, raw_data}`, the same shape for all 9 techniques (the "parser contract", see root `CLAUDE.md`) |
| `file_hash` | text | MD5 of the raw binary — anti-duplication gate for this lane |
| `created_at` | timestamptz | Ingestion time |

**Note for the owner**: this table currently has **0 rows** — it was at 1
row the last time it was checked (down from 3), which was flagged in the
project diary as an open incident to investigate, unrelated to the RAG work.
Worth a look before trusting any characterization query.

## 3. Governance & audit — `authorized_researchers`, `audit_log`, `agent_chat_log`

These three exist purely to answer "who did what, and were they allowed to."
None of them hold lab data.

### `authorized_researchers`
The whitelist. `email` is the primary key. `active=false` revokes access
without deleting history. `role` is currently descriptive only (not yet used
to scope *which* tools someone can call — everyone on the list gets the same
tool access today).

### `audit_log`
**One row per action** a pipeline or an agent tool performed — not per
conversation. `agent` names the process (`alchemy_ingestion_pipeline`, or an
agent tool name), `action` is what was attempted, `verdict` is
`ALLOW`/`DENY`/`ERROR`, `cause` explains why, `result` is the final outcome.
`actor_email` and `session_id` (added when the chat agent's identity model
was built) let a single conversation's tool calls be reconstructed. This
table is written **deterministically by SQL functions** (`agent_authorise()`,
`agent_log_exchange()`, `SECURITY DEFINER`), never directly by the language
model — see the RAG section below for why that boundary matters.

### `agent_chat_log`
**One row per question+answer exchange** in the RAG chat — a *coarser* unit
than `audit_log`. A single question can trigger several tool calls (several
`audit_log` rows) before the model produces one answer (one `agent_chat_log`
row). Both tables share `session_id`, so a full conversation can be
reconstructed at either granularity: "what did the person ask and what did
they get back" (`agent_chat_log`), or "exactly which SQL functions ran and
what did each one return" (`audit_log`).

## 4. The RAG corpus, explained end to end

This is the part that "se escapa" — so this section walks the whole pipeline
in order, table by table, rather than just listing columns.

### The mental model: a library card catalogue + the actual shelved text

`rag_documents` is the **card catalogue**: one row per source file (a paper,
a lab notebook, a protocol), holding *who wrote it, what journal, what DOI* —
never the actual text. `rag_chunks` is the **shelf**: one row per small
fragment of the actual text, each with its own vector embedding, always
linked back to its card via `document_id`. This split exists because
retrieval works over chunks (small enough to embed meaningfully and to fit
in an LLM's context) but *citation* works over documents (a reader wants "cite
the paper", not "cite fragment #4821").

### `rag_documents` — the card catalogue

| Column | What it means |
|---|---|
| `document_id` | PK |
| `file_name`, `file_path` | Where the archived copy lives under `data/rag_corpus/{public,internal,zotero}/` (container path) |
| `file_hash` | MD5 of the file bytes. **UNIQUE** — level 1 of the anti-duplication ladder below |
| `text_hash` | MD5 of the normalised title + first 3000 characters. Level 3 of the ladder, for documents with no DOI |
| `doi` | Digital Object Identifier, when it has one. Level 2 of the ladder |
| `title`, `authors`, `year`, `journal` | The citation fields |
| `csl_json` | The **full** bibliographic record in CSL-JSON (the format Zotero/Mendeley export) — `title`/`authors`/`year`/`journal` are a flattened convenience over this, `csl_json` is the source of truth |
| `doc_type` | `PAPER`, `SUPPORTING_INFORMATION`, `LAB_NOTEBOOK`, `PROTOCOL`, `THESIS`, `SOP` |
| `sensitivity` | `PUBLIC` / `INTERNAL` / `RESTRICTED` — derived from which sub-folder of `data/rag_corpus/` the file was dropped in, so labelling happens by *where you put the file*, not by remembering to tick a box. `INTERNAL`/`RESTRICTED` must never reach an external LLM unmasked |
| `metadata_source` | `PDF_HEURISTIC` < `CROSSREF` < `REFERENCE_MANAGER` < `MANUAL` — see "Why metadata_source exists" below |
| `n_pages`, `n_images`, `n_chars` | Physical facts about the file. `n_images` is not stored as pixels — the RAG never sees figures, only their captions, which travel as ordinary text |
| `needs_ocr` | `TRUE` when `n_chars` is too low to be worth chunking (a scanned page with no extractable text). Ingestion **must** skip these — vectorising an empty string succeeds without error and silently produces a document with zero useful chunks, which is a worse failure than an obvious crash |
| `n_chunks` | How many rows this document has in `rag_chunks` — a cheap consistency check: this number, compared against `SELECT count(*) FROM rag_chunks WHERE document_id = ...`, should always match |
| `parent_document_id` | Self-referencing FK: a Supporting Information row points at the paper it belongs to |

**The 3-level anti-duplication ladder** (`rag_find_existing_document()` in
`init_db.sql`, used by `src/rag_catalog_corpus.py`): a binary MD5
(`file_hash`) is a perfect fingerprint of the *bytes* but a terrible one of
the *paper*, because publishers stamp a per-download watermark on every page
— the same article downloaded twice yields two different files. So the
ladder tries, in order: (1) exact same file (`file_hash`), (2) same DOI
— catches the same paper arriving from a different source or watermark, (3)
same normalised title+header text — catches documents with no DOI at all
(lab notebooks, page proofs).

**Why `metadata_source` exists**: different ingestion routes disagree on
metadata quality. A bare PDF's embedded metadata often keeps only the
*corresponding* author, dropping the other eight. Crossref is public and
accurate but only knows what it was told. A human-curated Zotero library
(`REFERENCE_MANAGER`) is the most trustworthy automatic source. Every UPSERT
into `rag_documents` compares the incoming source's rank against the row's
current rank (`rag_source_rank()`) and only overwrites `title`/`authors`/
`doi`/`year`/`journal`/`csl_json` if the incoming source outranks the
existing one. This is what stopped a single-author PDF re-read from silently
erasing a verified 9-author Crossref record — a real bug this project hit.

### `rag_chunks` — the shelf

| Column | What it means |
|---|---|
| `id` | PK (named by LangChain convention, not ALCheMy's own) |
| `document_id` | FK → `rag_documents`, `ON DELETE CASCADE` |
| `text` | The chunk's literal text — **this is the only place the raw text lives** once chunking has happened |
| `embedding` | `VECTOR(1024)` — the semantic fingerprint from the local Ollama `bge-m3` model. 1024 is fixed by that model; switching embedding models means dropping and rebuilding every row here |
| `text_tsv` | A generated `tsvector` column (PostgreSQL's built-in full-text index), using the `simple` config deliberately — no stemming, so chemical nomenclature like `Zr6O4(OH)4` is not mangled the way an English stemmer would mangle it |
| `metadata` | JSONB copy of a few `rag_documents` fields (`file_name`, `file_hash`, `doc_type`, `sensitivity`) cached onto the chunk, so a search result can be filtered/cited without a join back to `rag_documents` |
| `created_at` | When the chunk was written |

**Filled by**: `src/rag_ingest_chunks.py` — see "one more thing: the n8n
chunking node vs. this script" below for how this relates to the master n8n
workflow.

**Retrieved by**: `rag_hybrid_search()`, a SQL function combining a vector
similarity search over `embedding` and a lexical search over `text_tsv`,
merged with Reciprocal Rank Fusion — this is the "hybrid search" the RAG
chat's SQL tool calls. `src/rag_query.py` is a CLI wrapper around the exact
same function, with **no LLM attached**, kept specifically so retrieval
quality can be judged independently of generation quality.

### The permission boundary: SQL functions, not free-text SQL

Nothing lets the chat model run arbitrary SQL. It can only call a fixed
catalogue of parameterised functions (`agent_search_synthesis`,
`agent_get_characterization`, `agent_sample_summary`, `agent_statistics`,
`agent_search_library`, described individually as rows in `data_dictionary`
where relevant, and enforced by `GRANT EXECUTE ... TO alchemy_agent` while
everything else is `REVOKE`d). Two independent layers matter here, and they
are not the same kind of control:

- **Soft control** — *which* tool the model decides to call. This is only as
  reliable as the model's judgement; it can be wrong.
- **Hard control** — *what each tool is physically capable of returning*,
  enforced by PostgreSQL regardless of what the model intended: row caps
  (`agent_row_limit()`, capped 1–200 no matter what is requested), which
  columns a function selects (`agent_get_characterization` never selects
  `data_json`, even if asked to), and the `alchemy_agent` role's own
  permissions (direct `SELECT`/`UPDATE`/`DROP` are denied at the database
  level, verified by testing all three).

`p_actor`/`p_session` are always the **first two parameters** of every
catalogue function, and the n8n workflow fills them from the already-validated
caller identity (`agent_authorise()`) — never from `$fromAI`. If the model
could declare on whose behalf it was acting, the audit trail would be
worthless: one hallucination could attribute a query to the wrong person.

## One more thing: the n8n chunking node vs. `rag_ingest_chunks.py`

Both exist, and they do the *same* splitter logic (same chunk size, same
overlap, same separators) — they are two entry points into the same table,
for two different situations:

- **`src/rag_ingest_chunks.py`** is what actually built the 87,765 rows in
  `rag_chunks` today. It exists because there was already a large, static
  corpus sitting on disk (958 documents pulled from Zotero and folders) that
  needed to be processed once, resumably, over many hours — a batch job, not
  an event. It is resumable by design (only processes
  `rag_documents WHERE n_chunks = 0` unless told `--force`), which a
  long-running n8n execution is not well suited for.
- **The n8n chunking node** in the ingestion workflow exists for the
  *ongoing* case: someone drops one new paper into `data/rag_corpus/` (or a
  future upload form submits one), and the workflow should catalogue,
  chunk, and embed *that one document* automatically, without anyone running
  a script by hand. It is the "keep the corpus alive after today" half of the
  system; `rag_ingest_chunks.py` was the "get the corpus to exist at all"
  half.

Because both write into the exact same `rag_chunks` table with the exact
same shape, a document can be indexed by either path interchangeably — the
resumability check (`n_chunks = 0`) means the two never race or double-index
the same document.
