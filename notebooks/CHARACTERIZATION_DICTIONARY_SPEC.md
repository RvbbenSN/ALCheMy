# 🔬 Characterization Specification & Multimodal Data Mapping

---

## 📌 Purpose of this Document
This document defines the **official field-by-field data mapping specification** for ALCheMy experimental characterizations:
1. **Powder X-Ray Diffraction (PXRD `.xrdml` XML files - PANalytical EMPYREAN)**.
2. **Thermogravimetric Analysis (TGA / ATG `.txt` TA Instruments SDT Q600 files)**.
3. **Fourier-Transform Infrared Spectroscopy (FTIR `.csv` Thermo Nicolet files)**.
4. **Inductively Coupled Plasma Optical Emission Spectroscopy (ICP-OES `.pdf` Analytical Reports)**.
5. **Organic Elemental Analysis (EA / CHNS `.pdf` Thermo FLASH 2000 Reports)**.
6. **Gas Adsorption & BET Surface Area (BET `.xls` Micromeritics 3Flex Reports)**.
7. **Variable-Temperature Powder X-Ray Diffraction (VT-XRD `.brml` Bruker D8 Advance Containers)**.
8. **Ultraviolet-Visible Spectroscopy (UV-Vis `.asc` / `.csv` PerkinElmer Lambda 1050 Files)**.
9. **Scanning Electron Microscopy (SEM `.jpg` Image + `.txt` Metadata - Hitachi TM-1000)**.

Each technique specification is divided into **2 distinct sections**:
- **SECTION 1:** Direct fields for the **Relational SQL Table** (`characterization_measurements`).
- **SECTION 2:** Complete structure for the **`data_json` Column (JSONB)** (`header_metadata` + `raw_data`).

### A. Sub-dictionary `header_metadata` (PXRD .xrdml)

Extracted 2026-08-22 after inspecting a real `.xrdml` file end-to-end (`24DRX0180-RS1883_CoPy.xrdml`) — the format turned out to carry far more than the curve geometry: full acquisition timing, radiation/optics/detector configuration, and instrument/software provenance.

## 📦 SECTION 2: Standardized `data_json` Column (JSONB) Structure - FTIR

### A. Sub-dictionary `header_metadata` (FTIR)

Re-checked 2026-08-22 against several real `.csv` files. Unlike PXRD/VT-XRD/TGA, **this format carries no header at all** — just the two numeric columns, nothing else. There is genuinely nothing more to extract from the file itself; `operator_name`/`instrument_name` remain fixed defaults because the file gives no way to know them.

**Critical bug fixed:** the old code split columns on `sep=r'[,;]'` (comma **or** semicolon at once). The data lake actually contains two different real conventions — most files use `;` as the column separator with `,` as the decimal point (e.g. `3,996747e+002;0,000000e+000`), one uses `,` as the column separator with `.` as the decimal point. Splitting on both characters at once cut every European-format number in half (`3,996747e+002` → garbage columns `3` and `996747e+002`), so **every FTIR spectrum ever parsed by the old code was wrong**. The parser now reads the first line to detect which of the two conventions applies before splitting.

| JSON Key | Data Type | `.csv` Source | Scientific Meaning |
| :--- | :--- | :--- | :--- |
| **`sample_name_raw`** | `String` | Base filename | Raw sample name — not present inside the file |
| **`column_separator_detected`** | `String` | *(Auto-detected: `;` or `,`)* | Which of the two real delimiter conventions this specific file used |
| **`spectral_range_cm-1`**| `Array[Float]` | `[min(x), max(x)]` | Infrared spectral range in wavenumbers cm-1 (e.g. `[399.7, 4000.1]`) |
| **`atr_crystal`** | `String` | *(Constant, not in file)* | ATR sampling accessory crystal material (`Diamond ATR`) |
| **`num_data_points`** | `Integer` | *(Data table row count)* | Total number of wavenumber points recorded in spectrum (e.g. `7469`) |

# 🖼️ TECHNIQUE 9: Electron Microscopy (SEM / FESEM / TEM `.jpg`/`.jpeg`/`.png` Image + optional `.txt` Instrument Metadata)

> **Re-derived/Re-checked 2026-08-22.** This technique is now split into two stages, matching
> the rest of the pipeline: a **deterministic parser** (`src/parse_microscopy_image.py`,
> `n8n` node `Parse Microscopy (.jpg)`) runs first and extracts everything the instrument's
> own companion `.txt` sidecar already records as fact - real magnification, beam voltage,
> working distance, printed scale-bar length, acquisition date/time, instrument model and
> serial. None of that needs an LLM to guess. Three real conventions confirmed by inspecting
> the actual data lake, auto-detected by sidecar content (not by technique tag, since the
> file format is what actually determines how to read it):
> - **SEM (Hitachi TM-1000)**, `.jpg` + `.txt`: `[SemImageFile]` INI-style `Key=Value` block.
>   Present for 1152 of the 1742 `.jpg` files under `SEM/`. The remaining ~590 `.jpg` files
>   without a `.txt` sidecar are EDX elemental-composition spectrum screenshots (paired with
>   a `.csv`), not micrographs at all - the parser degrades gracefully for these (empty
>   `header_metadata`, no crash, `companion_metadata_format: null`).
> - **FESEM (JEOL JSM-7900F)**, `.bmp` + `.txt`: a completely different `$KEY value` /
>   `$$KEY value` dollar-prefixed format (`$CM_INSTRUMENT`, `$CM_MAG`, `$$SM_WD`...). Some
>   images also carry `$AN_TEXT%N` annotation lines - real dimensions the **operator measured
>   by hand** with the SEM software's own calibrated cursor tool (e.g. `"X:19.875µm"`), kept
>   verbatim as `operator_cursor_annotations` since this is genuine measured data, not a
>   guess by anyone (human or AI). Image format here is `.bmp`, not `.jpg` - the router's
>   extension rule was extended to `^(jpg|jpeg|png|bmp)$` to match.
> - **TEM**, `.jpg`, **no sidecar at all**: the real magnification is embedded directly in
>   the filename instead (e.g. `..._MAG_X3000_001.jpg`, `..._SA-MAG_X25k_003.jpg`, where
>   `SA-MAG` = selected-area magnification, TEM's diffraction-mode shots) and is extracted
>   from there (`magnification_source: "filename"`). Each TEM sample folder also has a
>   `..._Microanalisis.docx` companion report - out of scope for this deterministic parser
>   (Word document, not raw instrument data); noted for a future dedicated report-ingestion
>   step rather than guessed at here.
>
> Any sidecar that doesn't match either recognized format falls back to a generic
> `Key=Value` scan and keeps the full raw dict under `header_metadata.raw_instrument_metadata`
> so nothing is lost even before a new instrument's format is characterized.
>
> **Known caveat:** the Gemini vision API's officially supported image MIME types do not
> include BMP. The AI qualitative-enrichment step may therefore fail for FESEM `.bmp` files
> specifically - this is expected and handled: it lands in the same audit-logged fallback
> path as any other AI failure (`AI_AGENT_EXTRACTION_FAILED`), and the deterministic
> metadata from this parser is unaffected either way, since the AI step runs strictly after
> and only adds the qualitative layer.
>
> **Only after** the deterministic parse does a lightweight vision-AI step run
> (`AI Agent - Image Analizer`), and its job was deliberately narrowed: it no longer attempts
> any quantitative measurement (the earlier version fabricated a numeric
> `estimated_particle_size_um` from pixel content, which is not something a general-purpose
> vision LLM can do reliably). It now only: (1) sanity-checks that the image is really a
> micrograph, (2) describes morphology in qualitative, hedged text, and (3) transcribes any
> scale-bar caption *literally printed on the image* if legible - reading printed text, not
> inferring a measurement. A dedicated merge node (`Merge AI Analysis - Microscopy`) combines
> the deterministic `header_metadata` with the AI's qualitative output into
> `raw_data.ai_vision_analysis`, so one record always carries both layers together, and
> restores fields (researcher email/name, file path, file hash) that the agent's structured
> output does not itself carry.
>
> `technique` is always declared explicitly by the uploader (form dropdown / webhook payload
> / data-lake folder name) - the AI is never asked to disambiguate SEM vs FESEM vs TEM, since
> that would be strictly less reliable than either the explicit tag or (when present) the real
> instrument name in the `.txt` sidecar.
