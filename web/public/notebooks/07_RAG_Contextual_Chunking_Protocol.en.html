07 · RAG — Contextual Chunking: Operational Protocol (Phase C-bis)

This notebook documents, incorporating authentic execution scripts and live database outputs, the end-to-end operational protocol followed to append one contextual sentence per chunk across the RAG corpus (utilising Anthropic's contextual retrieval methodology). It leverages an external model (Gemini, orchestrated via Antigravity) as a human-in-the-loop collaborator, without exposing either the production database or the prior embeddings generated by Ollama.

Purpose of this notebook: It serves not merely as an activity log, but as a reusable operational protocol for future projects requiring the delegation of bulk synthetic text generation to an external LLM under constrained session budgets, backed by automated verification without requiring exhaustive manual human auditing.

1. Rationale & Roadmap Alignment

This methodology is not an ad-hoc invention: it implements contextual retrieval, established by Anthropic and scheduled in the project roadmap since version 1 as pending implementation. Verbatim citation from ROADMAP_RAG_Y_GRAFO.md:

"Contextual chunking: prior to embedding, a lightweight LLM appends 1–2 contextual sentences to each chunk [...]. This is Anthropic's technique — yielding a 35% reduction in retrieval failure rates on its own."

When combined with lexical search (BM25) and neural reranking, Anthropic reports a 67% reduction in retrieval failures (from 5.7% to 1.9%). Standalone contextual embeddings, without the secondary components, achieve a 35% failure reduction.

The governing architectural constraint: the protocol dictates "prior to embedding". Context is not stored adjacent to vectors as superficial metadata—it is fused into the chunk text itself, and that composite string is embedded. Failure to adhere to this principle renders context generation futile: vector search engines compute cosine distances across vectors, never inspecting untokenised sidecar text.

Why deploy a sidecar table rather than appending columns directly to rag_chunks: An external generative model, possessing a documented failure history (Section 5), must never have write access to columns governing live production retrieval (embedding). If the sidecar generation experiences corruption, it can be purged and regenerated without risk. This same defensive principle justifies the implementation of embedding_v2 in Section 8: even the final embedding generation is barred from mutating primary vectors.

3. Step 1 — Exporting Document Batches

src/rag_export_context_batches.py serialises document-level JSON payloads into data/rag_context_batches/pending/. Batching at the document level (rather than per chunk) aligns with the fundamental premise of the technique: an LLM requires the entire document context to orient individual chunks within the broader research narrative. An isolated chunk lacks sufficient context to situate itself. Furthermore, document grouping consolidates ~87,765 chunk-level API calls into ~956 document-level prompts.

4. Operational Prompts for Gemini / Antigravity

This represents the exact prompt supplied to the Antigravity interface at the start of each session, targeting pending/. It incorporates defensive constraints established following the initial operational incident (Section 5.1), forbidding phrase recycling:

You will find JSON files in data/rag_context_batches/pending/ (or data/rag_context_batches/repairs/pending/ for a repair batch). Each one lists chunk_ids and the full text of the document they belong to. Follow each file's own "instructions" field exactly — one specific, non-generic sentence per chunk_id, grounded in what that exact chunk says. Never a generic template, never a "(part N)" counter standing in for a real difference, never a garbled or truncated word filling a gap, and never the same sentence (or a near-identical one) reused across multiple chunks. Process the files one at a time, in filename order, moving each finished one to the matching done/ folder as you go. Stop cleanly when pending/ is empty or you run out of session budget. Same hard limits as always: never edit any .py file, never touch the database, never open anything outside data/rag_context_batches/.

5. Verification Prior to Database Commitment

src/rag_import_context_batches.py never commits records to rag_chunk_context without passing verify(). If any document payload contains anomalies, the entire file is rejected and routed to rejected/, ensuring failures trigger immediate alerts rather than introducing silent omissions.

5.1 Incident 1 — Recycled Boilerplate Phrases

The initial bulk batch processed by Gemini satisfied structural schema checks (matching chunk_id counts, zero missing keys). However, manual inspection revealed that the model recycled 3 to 10 generic sentences across entire papers containing 100–250 chunks (for instance, looping 3 identical sentences across 227 consecutive chunks). Structural rules failed to catch this defect because the output remained well-formed JSON.

Remediation: Rule 5 was integrated into verify(): if a file contains >5 chunks and exhibits <50% unique sentence diversity, it is rejected. Retroactive evaluation across the 30 incident files yielded 30/30 detections with zero false positives on valid historical files.

5.2 Incident 2 — The Broken "(part N)" Template

A subtler artifact emerged following Rule 5 deployment: for a minority of chunks per document, the model populated a rigid boilerplate template—"This X chunk (part N) evaluates <broken fragment> regarding <title>"—inserting truncated or corrupted words into the variable slot. Because the part counter incremented dynamically, every sentence was technically unique, effortlessly satisfying diversity thresholds. This failure was identified solely by scanning imported text for regular expressions.

5.3 Incident 3 — Pre-Existing Historical Failures

Auditing the full database revealed 37 documents affected by the original phrase recycling failure, dating from before Rule 5 was deployed. The validation filter had not failed; rather, older data had bypassed the gate prior to its construction.

Key Takeaway: A newly deployed pipeline validation rule protects solely what is processed after its release. Data committed historically requires independent retroactive auditing.

6. Targeted Surgical Repairs vs Total Corpus Regeneration

src/rag_export_context_repairs.py implements two distinct repair modes tailored to the failure pattern:

  • --mode template (Incident 5.2): Where only a small fraction of chunks are corrupted (median <10%). Re-exporting the entire paper would discard hundreds of valid sentences. The script exports strictly the flagged chunk_id entries, supplying the complete document text as background context.
  • --mode recycled (Incident 5.3): Where the majority of chunks share duplicate text and authentic allocations cannot be distinguished. The entire document is regenerated from scratch.

Both modes route through standard verify() rules, segregating payloads in data/rag_context_batches/repairs/ to avoid polluting incoming document queues.

7. Segmented Wave Operations under Constrained Budgets

Antigravity sessions operate under temporal allocation limits. The resumption protocol guarantees operational continuity:

  1. Execute --status prior to each wave: if pending/ is populated, resume uncompleted batches from previous sessions before exporting new documents.
  2. rag_export_context_batches.py --limit N targets only documents lacking contextual sentences, preventing duplicated processing.
  3. If an execution session terminates abruptly, processed documents reside safely in done/, while remaining items persist in pending/.
  4. --apply commits strictly verified records; invalid files are routed to rejected/ without touching database state.

8. Phase D — From Stored Context to Vector Influence

Populating rag_chunk_context does not improve search retrieval on its own: it is inert text. Fulfilling Anthropic's benchmark requires embedding the composite string context + chunk.

Explicit Architectural Decision: Embeddings are written to a dedicated column (rag_chunks.embedding_v2), never overwriting primary embedding. Contextual sentences were authored by an external generative model with a documented error history (Sections 5.1–5.3); expecting human operators to manually audit ~88,000 sentences is unrealistic. Maintaining a separate vector column eliminates operational risk: the worst-case rollback is simply UPDATE rag_chunks SET embedding_v2 = NULL.

src/rag_reembed_context.py computes embedding_v2 locally using the identical Ollama model (bge-m3) employed for primary embeddings.

9. Generalisable Operational Checklist

  1. Enforce privacy boundaries via SQL clauses, never prompt directives. A model can disregard prompt instructions; it cannot access data withheld by database queries.
  2. Utilise sidecar tables rather than mutating production schemas during asynchronous external LLM processing.
  3. Validate before committing, rejecting entire batch units upon failure. Transparent failures are inexpensive to remediate; silent corruptions escape notice.
  4. Structural validation does not equate to content validation. Malformed or repetitive text can reside inside valid JSON schemas.
  5. New validation gates protect only future ingestions. Historical database records require independent retroactive auditing.
  6. Apply surgical repairs for localized errors; regenerate entire units for pervasive failures.
  7. Batch at the semantic unit requiring complete context (documents rather than chunks).
  8. Implement file-based handoffs with explicit status tracking to decouple workflows from session budget cut-offs.
  9. Write downstream representations into isolated columns and execute comparative A/B testing prior to replacing active production assets.
