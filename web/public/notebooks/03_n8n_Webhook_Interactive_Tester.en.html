🧪 ALCheMy — Interactive n8n Webhook Tester

This notebook pursues two main objectives:

  1. Test all pipeline ingestion scenarios: A "happy path" case for each of the 9 deterministic and microscopy techniques plus the 2 AI-driven (PDF) techniques, alongside every fallback mechanism (unauthorised email, file size exceeded, duplicate entry, missing sample_code, unrecognised technique, invalid file extension, human L2 rejection, approval timeout, and AI agent extraction failure).
  2. Define the skeleton of a Python client (ALCheMyIngestionClient) for the ingestion webhook. This establishes the interface for a production API: while it currently communicates over HTTP directly with n8n, the endpoint contract (submit(file_path, technique, sample_code, ...)) is identical to what a future FastAPI wrapper or backend service would expose.

⚠️ Prerequisites

  • docker compose up -d must be active (running n8n, task runners, and PostgreSQL).
  • The ALCheMy workflow must be active in n8n, with the Webhook node enabled. If you followed this setup session, it is already enabled (it was previously disabled by default). If it is disabled in the editor, this notebook will cease to receive responses in mode="prod".
  • Refresh (F5) your n8n browser tab prior to execution to avoid executing an out-of-sync workflow version.
  • Install required dependencies: pip install requests psycopg2-binary python-dotenv.

🧩 Ingestion Client Skeleton & API Wrapper

ALCheMyIngestionClient wraps the multipart POST request directed to the n8n webhook. It is intentionally lean: it exposes a single public method (submit), containing no intrinsic business logic (which resides within the n8n workflow). Should a dedicated API layer (e.g. FastAPI) be deployed in front of n8n in the future—for genuine authentication, rate limiting, or pre-validation—the submit(...) contract will remain unchanged; only the underlying transport layer will change.

🧯 Part 2 — Fallback & Error-Handling Scenarios

Each fallback event logs an entry into audit_log with typed verdict, cause, and result fields (governed by workflows/error_payloads_matrix.csv). The first 7 scenarios are fully automated from within this notebook; the remaining 3 (human rejection, approval timeout, and AI agent failure) require human interaction or temporal delays. These are documented systematically rather than simulated arbitrarily, as mocking them would present a misleading sense of test coverage.

1. Unauthorised Email (Whitelist Verification)

Auto-Enroll Whitelist automatically registers any new incoming email address as active (demonstration self-enrolment). However, it does not reactivate an address explicitly disabled by an administrator (ON CONFLICT ... DO UPDATE SET last_seen = ... leaves active untouched). Consequently, to test this fallback mechanism, an email address must first be deactivated manually.

2. File Size Exceeded (> 10 MB)

A synthetic padding file is generated programmatically rather than relying on the presence of an authentic file exceeding 10 MB in the Data Lake.

3. Duplicate Measurement Ingestion

Re-submits the identical PXRD file used in the happy path test (run the Part 1 PXRD cell first, otherwise there will be no existing record to trigger a duplicate collision).

4. Missing sample_code

No sample_code is supplied, and the filename contains no recognisable sample naming pattern (RS\d+, IEF-\d+, RSMix\d+, LP\d+).

5. Unrecognised Analytical Technique

6. Invalid File Extension for Deterministic Technique

technique="PXRD" is declared, but an FTIR .csv file is uploaded. The deterministic technique-extension routing table contains no matching rule to accept this payload.

7. Invalid File Extension for AI Document Extraction (PDF)

technique="ICP-OES" is declared, but an .xrdml file is submitted instead of a .pdf.

8. Human Rejection during L2 Approval (Manual Inspection)

This test cannot be automated programmatically: it must be triggered manually, followed by clicking Decline in the approval notification email sent to researcher@hidden (or the configured researcher_email recipient).

  1. Execute the cell below to trigger an AI document extraction.
  2. If the agent's confidence score evaluates to below 85%, an approval email containing Approve and Disapprove actions will be dispatched.
  3. Click Disapprove. The workflow should log the event into audit_log with the cause REJECTED_BY_RESEARCHER and abort database insertion.
  4. If confidence evaluates to above 85%, no approval prompt will trigger. Retry with an alternative PDF report, or temporarily lower CONFIDENCE_THRESHOLD within the Confidence Evaluator node specifically for this test.

9. Approval Timeout (Time-Dependent Manual Verification)

Triggered identically to the scenario above, but do not respond to the email notification. After 5 minutes have elapsed (resumeAmount: 5 in the Send message and wait for response node), the workflow automatically diverts to the error branch, recording the cause APPROVAL_TIMEOUT_OR_ERROR. Rather than blocking execution within the notebook, inspect audit_log after 5 minutes:

SELECT * FROM audit_log ORDER BY created_at DESC LIMIT 5;

10. AI Agent Extraction Failure (Environment Manipulation)

To force this fallback reliably, break the upstream LLM API call deliberately:

  1. In .env, set GEMINI_API_KEY to an invalid string (backup the authentic key beforehand).
  2. Execute docker compose restart n8n.
  3. Run the cell below using any PDF or image payload.
  4. The endpoint should return HTTP 400 with cause AI_AGENT_EXTRACTION_FAILED, recorded in audit_log.
  5. Restore the authentic GEMINI_API_KEY and restart the n8n container once more.

This process is not automated within the notebook, as mutating .env variables and restarting infrastructure containers programmatically carries operational risks.

🤖 Automated End-to-End Test Suite

The individual cells above facilitate granular inspection of isolated test cases. To confirm overall pipeline health comprehensively, an automated test script executes all 9 happy paths and 7 automated fallbacks simultaneously. Furthermore, it verifies that the resulting record landed in characterization_measurements with the complete metadata payload extracted by the parser (rather than merely checking for an HTTP 200 response):

python src/verify_webhook_pipeline.py                # complete test suite
python src/verify_webhook_pipeline.py --happy        # happy paths only
python src/verify_webhook_pipeline.py --fallbacks    # fallback paths only
python src/verify_webhook_pipeline.py --only PXRD    # isolated single technique
python src/verify_webhook_pipeline.py --table characterization_measurements  # target canonical table

The cell below passes MEASUREMENTS_TABLE (defined in the first cell of the notebook) to the verification script automatically. Adjust that variable to test against the canonical production table instead of the staging table.

This test suite exists because the pipeline presents multiple independent failure surfaces (the n8n Python sandbox environment, multipart binary handling, technique-and-extension routing tables, and PostgreSQL foreign key constraints). Manual testing allows regressions to escape unnoticed: fixing an issue for one technique can silently disable or corrupt another.

⚠️ Constraints of the n8n Python Sandbox (Empirical Laboratory Findings)

Python Code nodes in n8n do not execute within a standard CPython interpreter. Instead, they run within a restricted sandbox that intercepts and blocks standard operations without transparent warnings. All behaviours below have been validated empirically against the active runtime environment:

Operation Observed Error Recommended Workaround
Bare open is prohibited name 'open' is not defined Insert import io; open = io.open at top of node
open(...) in text mode ('r') is broken 'NoneType' object is not callable Read in binary mode ('rb') and decode manually via .decode(...)
getattr and type are prohibited name 'getattr' is not defined Avoid their use; rely on try/except blocks and inspect str(e)
Binaries arrive as pointers rather than payloads base64.b64decode produces corrupt bytes Pre-convert binary inputs via a Move Binary Data node (keepAsBase64)

Additionally, an architectural quirk of the Webhook node must be noted: it re-indexes all uploaded files under a uniform naming convention (data_file0, data_file1...), disregarding the original multipart form field names. Consequently, metadata .txt sidecars arrive as data_file1 and must be renamed explicitly within Normalize Webhook Body.

Maintenance note: parser implementations exist in two locations (in standalone src/parse_*.py files and embedded directly inside n8n Code nodes). Synchronising them manually is error-prone and caused microscopy parsers in n8n to lag behind JEOL support for several months. To synchronise them deterministically:

python src/sync_parsers_to_n8n.py --dry-run   # inspect divergence
python src/sync_parsers_to_n8n.py             # push updates from src/ to n8n

🧪 The AI Extraction Pipeline (ICP / EA): Experimental Validation & HITL Rationale

This document extraction branch previously inserted fabricated chemical data into the production database. It is therefore essential to record the root cause of the incident and the verification measures implemented.

The Failure Incident

When processing analytical report 24AQ0245 (ICP quantification of Fe, Ni, and P), the AI agent returned the following payload with an auto-assigned confidence score of 95%:

Field Source PDF Report Content AI Agent Output
Analyst Laura Garcia Firgaira John Doe
Date 17/06/2024 2023-10-26
Quantified Elements Fe, Ni, P Ni, Fe, Co, Mg, Ca (omitting P)
Ni Concentration 10.8 ± 0.5 25.12

None of these values appeared within the source document: the model fabricated the entire payload based on the filename and the system prompt.

Root Cause Analysis

The PDF binary never reached the model. The passthroughBinaryPdfs configuration parameter in the agent node forwards only binaries explicitly tagged as PDF, whereas the file arrived labelled as application/octet-stream (the fallback MIME type assigned by HTTP clients when an extension is unrecognised). Bereft of input document content, the model hallucinated from the only context available: the prompt instructions. Normalize Webhook Body now enforces correct mimeType resolution dynamically based on the verified file extension.

Key Engineering Takeaway

The 85% confidence threshold provided zero protection. Because the AI model self-evaluates its confidence, an ungrounded hallucination produces an equally ungrounded confidence score: the agent assigned 95% confidence to completely fabricated numbers. A safeguard that relies on the very system it is designed to audit is fundamentally ineffective. The failure was detected solely by cross-referencing model output against the authentic PDF document.

Current Status

Extraction now operates reliably: processing that identical report currently yields Laura Garcia Firgaira, CENTRAL RESEARCH LABORATORIES, Ni 10.8 ± 0.5, and P 21.4 ± 1.1, matching the source report exactly.

Nevertheless, autonomous L4 database insertion remains deliberately disabled: both branches of the If - Needs Human Approval? node route to human email verification, ensuring no PDF data enters the database without direct operator oversight. Prior to re-enabling autonomous ingestion, extraction fidelity must be verified across multiple authentic analytical reports (to date, only one report has been fully validated; evaluation of the second was suspended when free Gemini API credits were depleted), after which the FALSE output of the If node may be reconnected to DB Update.

Data Modelling Consideration

A single PDF report can report analyses for multiple distinct samples (for example, the ICP document covers both SMP-0012 and SMP-0015). However, the database ingestion inserts a single record mapped to the solitary sample_code passed in the HTTP request. An architectural decision is required to establish whether multi-sample documents should be decomposed into separate database records.
