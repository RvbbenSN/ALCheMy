🔬 Cuaderno 02: Arquitectura del lago de datos multimodal y estrategia de procesamiento de caracterización

Proyecto: ALCheMy - Laboratorio inteligente de química de materiales
Autor: Rubén Serrano Nieto & AI Agent Pair
Fecha: Agosto de 2026

📌 Resumen ejecutivo y propósito

Este cuaderno actúa como cuaderno de registro maestro interactivo y documentación arquitectónica para el subsistema de ingesta de caracterizaciones multimodales de ALCheMy.

En él se detalla:

  1. La arquitectura del lago de datos (data/raw_datalake/): La catalogación, aplanamiento y depuración de los ficheros de instrumentación analítica crudos correspondientes a 9 técnicas de caracterización.
  2. El modelo de base de datos relacional y JSONB (characterization_measurements): La estructuración en PostgreSQL de los registros espectroscópicos, termogravimétricos, de fisisorción y ópticos de alta dimensionalidad.
  3. El módulo de procesamiento determinista en Python (src/characterization_parser.py): Las funciones en Python de alto rendimiento y coste nulo diseñadas para la extracción automatizada de datos (<1 ms por fichero).
  4. La estrategia de ingesta híbrida con flujos n8n: La arquitectura modular que desacopla la ejecución de scripts deterministas del uso de agentes de IA basados en LLM (encargados de extraer informes en PDF y analizar imágenes SEM).

🗂️ Paso 1: Inventario del lago de datos multimodal (9 técnicas analíticas)

Para prevenir problemas de anidamiento excesivo de directorios, redundancia de ficheros y dependencias con licencias de software propietario, el lago de datos crudo se organizó en 9 directorios planos bajo data/raw_datalake/ (montados 1:1 en Docker en <path omitted>):

🏛️ Paso 2: Esquema relacional y JSONB en base de datos (characterization_measurements)

Para garantizar consultas SQL de alto rendimiento y mantener la flexibilidad ante cargas experimentales heterogéneas, las medidas de caracterización se almacenan en una tabla secundaria vinculada mediante sample_code:

CREATE TABLE IF NOT EXISTS characterization_measurements (
    measurement_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    sample_code VARCHAR(50) NOT NULL REFERENCES synthesis_experiments(sample_code) ON DELETE CASCADE,
    technique VARCHAR(30) NOT NULL, -- e.g. PXRD, TGA, FTIR, ICP_OES, EA, BET, VT-XRD, UV_VIS, SEM
    measurement_tag VARCHAR(100) DEFAULT 'as_synthesized',
    operator_name VARCHAR(100),
    instrument_name VARCHAR(100),
    file_name VARCHAR(255) NOT NULL,
    raw_file_path TEXT NOT NULL,
    data_json JSONB NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- High-speed JSONB GIN index for nested web app queries
CREATE INDEX IF NOT EXISTS idx_char_jsonb ON characterization_measurements USING gin (data_json);

Estructura estandarizada de la carga útil en data_json

Cada técnica completa dos subdiccionarios principales dentro de data_json:

  1. header_metadata: Parámetros de instrumental, longitud de onda de radiación, masa inicial de muestra, modo óptico, fecha y hora de registro e identificadores de muestra.
  2. raw_data: Vectores numéricos de alta densidad (x_label, y_label, x, y) o conjuntos estructurados multitemperatura (temperature_series, vector de objetos para VT-XRD).

💡 Paso 3: Hallazgos técnicos clave entre formatos

🔓 1. Contenedores .brml no cifrados de Bruker (VT-XRD)

  • Hallazgo: Los ficheros .brml son archivos ZIP estándar que alojan archivos XML sin cifrado (RawData0.xml, RawData1.xml... MeasurementContainer.xml).
  • Rampa multitemperatura en VT-XRD: Cada fichero .brml contiene pares de ficheros XML: RawData(2*i) almacena el escalón térmico registrado (por ejemplo 29 °C, 39 °C, 49 °C... 500 °C), mientras que RawData(2*i + 1) alberga los 3.145 puntos de intensidad de difracción medidos a dicha temperatura.
  • Impacto: Lectura 100 % nativa en Python mediante zipfile y xml.etree.ElementTree en <1 ms, sin depender de software propietario.

⚖️ 2. Termogravimetría de 7 señales de TA Instruments (TGA)

  • Hallazgo: Las termobalanzas SDT Q600 registran 7 señales instrumentales en tiempo real: tiempo (min), temperatura del horno (°C), masa (mg), flujo de calor (mW), diferencia térmica en el crisol (°C), voltaje del termopar (µV) y caudal de purga de la muestra (mL/min).
  • Impacto: Extracción íntegra en data_json, permitiendo representar simultáneamente la pérdida gravimétrica de masa en TGA y las transiciones térmicas de fase por calorimetría diferencial de barrido (DSC).

🖼️ 3. Calibración automática de la barra de escala en SEM Hitachi TM-1000

  • Hallazgo: Cada micrografía SEM en formato .jpg va acompañada de un fichero de texto auxiliar .txt generado por el instrumento, que recoge los campos Magnification (por ejemplo 300x), MicronMarker (por ejemplo 300 um), AcceleratingVoltage (15000V) y Detector (BSE).
  • Impacto: Eliminación total de la medición manual de escalas. Python lee directamente la calibración y permite que modelos de visión basados en LLM describan sistemáticamente la morfología cristalina.

🤖 Paso 4: Estrategia de ingesta híbrida y granular con n8n

Para asegurar estabilidad operativa, coste cero de API en datos numéricos y un aislamiento completo de errores, el flujo de ingesta de n8n se estructura según una arquitectura de enrutador modular:

  1. Nodo selector por extensión (enrutador): Evalúa las rutas de los ficheros entrantes del lago de datos.
  2. Subflujos de procesamiento determinista (95 % de los datos): Los ficheros con extensiones .xrdml, .brml, .txt, .csv y .xls ejecutan funciones de Python desde src/characterization_parser.py en <1 ms sin consumo de API.
  3. Subflujos de extracción con LLM (5 % de los datos): Los informes analíticos no estructurados en .pdf (ICP-OES y EA CHNS) se derivan a nodos de extracción LLM configurados con CHARACTERIZATION_DICTIONARY_SPEC.md como instrucción de sistema (System Prompt).
  4. Subflujo de visión con LLM: Las imágenes SEM en .jpg se procesan mediante modelos de visión por IA para nutrir el campo de descripción morfológica ai_vision_analysis.

🏁 Resumen de logros

  • Lago de datos saneado y aplanado: 9 técnicas analíticas catalogadas en directorios planos sin anidamiento.
  • Especificación maestra redactada: methodology/CHARACTERIZATION_DICTIONARY_SPEC.md recoge las expresiones XPath, columnas SQL y esquemas JSONB.
  • Módulo de procesamiento en Python desplegado: src/characterization_parser.py validado exhaustivamente en todos los formatos.
  • Preparado para canalización en n8n: Montaje de Docker ./data:<path omitted> listo para la sincronización automatizada hacia la base de datos PostgreSQL alchemy_db.

  • En el Paso 1 (línea 23 del original), el paréntesis queda formalmente abierto con dos puntos al final en el original: (mounted 1:1 inside Docker at <path omitted>:. Se ha mantenido <path omitted> respetando la sanitización, cerrando la estructura sintáctica.
  • En el Paso 3 (apartado 3), el metadato del instrumento recoge 300 um (con 'u' simple en lugar del carácter 'µ'). Se ha conservado literalmente como 300 um al tratarse del identificador de texto exacto del fabricante.
  • En el Paso 4 (resumen final), la especificación de montaje de Docker figura como ./data:<path omitted>. Si procede para la documentación web, convendría indicar la ruta de montaje interna de destino completa del contenedor.
