🧪 ALCheMy — Probador interactivo del webhook de n8n

Este cuaderno persigue dos objetivos fundamentales:

  1. Validar exhaustivamente la casuística de la canalización de ingesta: un caso de éxito (happy path) para cada una de las 9 técnicas deterministas y de microscopía más las 2 técnicas procesadas mediante IA sobre documentos PDF, junto a la totalidad de las ramas de contingencia (fallbacks: correo no autorizado, tamaño de fichero excedido, registro duplicado, ausencia de sample_code, técnica no reconocida, extensión de fichero no válida, rechazo manual en aprobación L2, expiración temporal de aprobación y fallo del agente de IA).
  2. Definir la estructura de un cliente en Python (ALCheMyIngestionClient) para el webhook de ingesta: la base para una futura API pública en producción. Aunque actualmente se comunica mediante peticiones HTTP directas con n8n, el contrato formal de invocación (submit(file_path, technique, sample_code, ...)) coincide con el que expondría un servicio backend desacoplado en FastAPI.

⚠️ Requisitos previos a la ejecución

  • El entorno docker compose up -d debe encontrarse en ejecución activa (contenedores de n8n, ejecutores auxiliares y base de datos PostgreSQL).
  • El flujo de trabajo ALCheMy debe estar activo en n8n, y el nodo Webhook debe figurar habilitado. Si siguió la sesión de configuración inicial, ya se encuentra en este estado (inicialmente venía inactivo por defecto). Si se desactiva manualmente desde el editor, este cuaderno dejará de recibir respuesta al operar en mode="prod".
  • Actualice (F5) la pestaña del navegador con la interfaz de n8n antes de ejecutar las celdas, evitando así discrepancias con versiones no sincronizadas del flujo.
  • Asegure la instalación de las dependencias necesarias: pip install requests psycopg2-binary python-dotenv.

🧩 Estructura del cliente y API de ingesta

La clase ALCheMyIngestionClient encapsula las peticiones multipart POST dirigidas al webhook de n8n. Se ha concebido intencionadamente con una arquitectura ligera: un único método público (submit), sin lógica de negocio propia (la cual se delega íntegramente en el flujo de trabajo). Si en el futuro se despliega una capa API dedicada frente a n8n (mediante FastAPI para gestionar autenticación estricta, control de tasa de peticiones o validación previa de esquemas), el contrato funcional de submit(...) se mantendrá inalterado, modificándose exclusivamente el mecanismo de transporte subyacente.

Se evalúa un caso práctico para cada una de las 11 combinaciones soportadas de técnica y enrutamiento: 6 procesadores deterministas convencionales, 3 flujos de microscopía (SEM, FESEM y TEM, ilustrando en FESEM el envío complementario de metadatos del instrumento) y 2 canales mediante agentes de IA aplicados a informes en formato PDF (ICP-OES y EA).

🧯 Parte 2 — Casuísticas de contingencia y control de errores (Fallbacks)

Cada contingencia genera un registro en la tabla audit_log clasificando formalmente los campos verdict, cause y result (según la especificación workflows/error_payloads_matrix.csv). Los primeros 7 casos se encuentran totalmente automatizados en este cuaderno. Los 3 restantes (rechazo humano, expiración temporal de la aprobación y caída del agente de IA) exigen intervención de un operador o esperas de reloj reales; se describen minuciosamente en lugar de forzar simulaciones ficticias en el cuaderno, evitando proyectar una falsa verificación de cobertura.

1. Dirección de correo no autorizada (Lista blanca)

El nodo Auto-Enroll Whitelist da de alta cualquier dirección de correo nueva con estado activo (mecanismo de autorregistro para demostraciones). No obstante, no reactiva aquellas direcciones que un administrador haya bloqueado expresamente (ON CONFLICT ... DO UPDATE SET last_seen = ... no altera el campo active). En consecuencia, para verificar esta contingencia resulta necesario revocar previamente un usuario de manera manual.

2. Tamaño de fichero excedido (> 10 MB)

Se genera dinámicamente un archivo sintético de prueba para superar el límite establecido, prescindiendo de la necesidad de almacenar ficheros voluminosos reales en el lago de datos.

3. Registro de medida duplicada

Reenvío del mismo fichero de PXRD utilizado en el caso de éxito (ejecute previamente la celda de PXRD de la Parte 1; de lo contrario, el sistema no detectará duplicidad alguna).

4. Ausencia de sample_code

Petición desprovista del identificador sample_code, cuyo nombre de archivo no contiene ningún patrón de muestra identificable (RS\d+, IEF-\d+, RSMix\d+, LP\d+).

5. Técnica analítica no reconocida

6. Extensión no válida para técnica determinista

Se especifica technique="PXRD", pero se transfiere un fichero .csv de FTIR. El enrutador determinista (asociación técnica-extensión) carece de reglas que validen dicha correspondencia.

7. Extensión no válida para procesamiento mediante IA (PDF)

Se declara technique="ICP-OES", pero se remite un fichero .xrdml en lugar de un documento .pdf.

8. Rechazo humano en fase de aprobación L2 (manual)

Este ensayo no puede automatizarse íntegramente: precisa ejecución activa y posterior pulsación de la acción Decline en el correo de validación remitido a researcher@hidden (o a la dirección asignada en researcher_email).

  1. Ejecute la celda inferior para iniciar la extracción mediante IA.
  2. Si el índice de confianza del agente se sitúa por debajo del 85 %, se recibirá un correo con las opciones Approve y Disapprove.
  3. Seleccione Disapprove. El flujo registrará en audit_log el motivo REJECTED_BY_RESEARCHER y cancelará la inserción del ensayo.
  4. Si la confianza supera el 85 %, el flujo no solicitará confirmación humana. Repita el ensayo con otro informe PDF o reduzca transitoriamente el valor de CONFIDENCE_THRESHOLD en el nodo Confidence Evaluator.

9. Expiración de tiempo de aprobación (manual, dependiente del tiempo)

Utiliza el mismo desencadenante que el caso precedente, pero omitiendo deliberadamente responder al correo. Transcurridos 5 minutos (resumeAmount: 5 en el nodo Send message and wait for response), el flujo deriva automáticamente a la rama de error registrando la causa APPROVAL_TIMEOUT_OR_ERROR. Para no bloquear la celda durante este intervalo, consulte la tabla audit_log transcurrido el tiempo límite:

SELECT * FROM audit_log ORDER BY created_at DESC LIMIT 5;

10. Fallo operativo del agente de IA (manual, mediante alteración de entorno)

Para provocar esta contingencia de forma fehaciente es preciso interrumpir la comunicación con el modelo LLM:

  1. En el fichero .env, altere temporalmente el valor de GEMINI_API_KEY (respaldando previamente la clave original).
  2. Ejecute en terminal docker compose restart n8n.
  3. Ejecute la celda correspondiente empleando cualquier fichero PDF o imagen de prueba.
  4. El servicio responderá con un código HTTP 400 asociado a la causa AI_AGENT_EXTRACTION_FAILED, documentada en audit_log.
  5. Restituya la variable GEMINI_API_KEY legítima y reinicie nuevamente el contenedor de n8n.

Este procedimiento no se ejecuta de forma automática en el cuaderno para preservar la integridad operativa del entorno de contenedores.

🤖 Batería de verificación automatizada integral

Las celdas individuales permiten examinar cada casuística de forma aislada y pormenorizada. Para contrastar la integridad global de la canalización de ingesta, se dispone de un script que evalúa simultáneamente los 9 casos de éxito y los 7 fallbacks automatizables. Además, el script comprueba que el registro resultante se haya insertado en characterization_measurements conteniendo todos los metadatos analíticos pertinentes (y no limitándose a validar una respuesta HTTP 200):

python src/verify_webhook_pipeline.py                # evaluación completa
python src/verify_webhook_pipeline.py --happy        # únicamente casos de éxito
python src/verify_webhook_pipeline.py --fallbacks    # únicamente contingencias
python src/verify_webhook_pipeline.py --only PXRD    # técnica aislada
python src/verify_webhook_pipeline.py --table characterization_measurements  # fuerza la tabla canónica

La celda inferior transmite automáticamente la variable MEASUREMENTS_TABLE (definida al comienzo del cuaderno) al script de verificación. Modifique dicha variable si desea dirigir las pruebas contra la tabla canónica en lugar de la tabla de ensayo.

Esta suite automatizada es fundamental dado que el sistema integra múltiples puntos de fallo desacoplados (el entorno aislado de ejecución en Python de n8n, la gestión de datos binarios multipart, las tablas de enrutamiento por extensión y las restricciones de clave foránea en PostgreSQL). La validación puramente manual propiciaba la aparición de regresiones: la corrección de un módulo podía comprometer inadvertidamente la funcionalidad de otro.

⚠️ Restricciones operativas del entorno de ejecución de Python en n8n

Los nodos Code en Python no se ejecutan sobre un intérprete CPython convencional, sino en un entorno restringido (sandbox) que intercepta determinadas instrucciones sin emitir advertencias detalladas. Los siguientes comportamientos se han determinado empíricamente en el entorno de ejecución activo:

Operación Error observado Solución adoptada
open convencional bloqueado name 'open' is not defined Incluir import io; open = io.open al inicio del script
open(...) en modo texto ('r') inoperativo 'NoneType' object is not callable Lectura en modo binario ('rb') y decodificación explícita con .decode(...)
Bloqueo de getattr y type name 'getattr' is not defined Omitir su uso; capturar excepciones mediante try/except y evaluar str(e)
Recepción de binarios como referencias y no como datos base64.b64decode produce datos corruptos Conversión intermedia con el nodo Move Binary Data (keepAsBase64)

Asimismo, debe considerarse una particularidad técnica del nodo Webhook: renombra sistemáticamente los ficheros recibidos bajo un identificador genérico secuencial (data_file0, data_file1...), omitiendo los nombres de campo originales del formulario multipart. Por ello, el fichero de texto con metadatos ingresa como data_file1 y debe reasignarse formalmente en el nodo Normalize Webhook Body.

Aviso de mantenimiento: el código de los procesadores analíticos se encuentra duplicado (en los ficheros independientes src/parse_*.py y embebido dentro de los nodos Code de n8n). La sincronización manual resulta propensa a desajustes y provocó que el procesamiento de microscopía en n8n operase desactualizado respecto a JEOL durante meses. Para asegurar la paridad de versiones:

python src/sync_parsers_to_n8n.py --dry-run   # comprobar divergencias
python src/sync_parsers_to_n8n.py             # propagar desde src/ hacia n8n

🧪 La rama de extracción mediante IA (ICP / EA): validación experimental y supervisión HITL

Esta canalización llegó a insertar datos químicos erróneos en la base de datos de producción. Por rigor metodológico, se documenta tanto el origen del incidente como el protocolo de verificación diseñado.

Descripción del fallo

Durante el procesado del informe 24AQ0245 (cuantificación por ICP de Fe, Ni y P), el agente de IA generó el siguiente resultado asignándole un índice de confianza del 95 %:

Variable Contenido real del informe PDF Valor generado por el modelo
Analista Laura Garcia Firgaira John Doe
Fecha 17/06/2024 2023-10-26
Elementos analizados Fe, Ni, P Ni, Fe, Co, Mg, Ca (sin cuantificar P)
Ni 10,8 ± 0,5 25,12

Ninguno de estos registros figuraba en el documento original: el modelo construyó la respuesta infiriéndola del nombre del archivo y de las directrices del prompt.

Causa fundamental

El contenido binario del PDF nunca llegó a transferirse al modelo. El parámetro passthroughBinaryPdfs en el nodo del agente únicamente transmite archivos identificados formalmente como PDF, mientras que el fichero se recibió etiquetado como application/octet-stream (asignación por defecto de clientes HTTP ante extensiones desconocidas). Al carecer de documento de entrada, el modelo respondió proyectando las instrucciones del prompt. Actualmente, el nodo Normalize Webhook Body asigna dinámicamente el mimeType adecuado basándose en la extensión real del fichero.

Conclusión técnica crítica

El umbral de confianza del 85 % carecía de valor como filtro de seguridad. Dado que el propio modelo autocalibra su confianza, cuando se produce una alucinación sobre los datos, se alucina igualmente el parámetro de certidumbre: asignó un 95 % a una serie de datos inventados. Un control de calidad sustentado sobre el mismo sistema que se pretende fiscalizar resulta ineficaz. La incidencia fue identificada únicamente mediante la auditoría manual contrastando la respuesta con el documento fuente.

Estado operativo actual

El módulo procesa correctamente: ante ese mismo informe reproduce fielmente Laura Garcia Firgaira, CENTRAL RESEARCH LABORATORIES, Ni 10,8 ± 0,5 y P 21,4 ± 1,1, en concordancia con el informe.

No obstante, la inserción desatendida en base de datos (L4) permanece intencionadamente inhabilitada: las dos salidas del nodo condicional If - Needs Human Approval? convergen en la notificación de aprobación por correo electrónico, impidiendo el ingreso de datos procedentes de PDF sin supervisión de un operador. Para reactivar el modo autónomo será necesario validar la tasa de acierto frente a múltiples informes analíticos reales (hasta la fecha solo se ha auditado uno; el segundo no pudo completarse al haberse agotado la cuota de la API de Gemini) y restituir la conexión entre la salida FALSE del nodo If y la operación DB Update.

Consideraciones sobre el modelado de datos

Un único informe en PDF puede contener resultados para múltiples muestras (el informe de ICP incluye determinaciones para SMP-0012 y SMP-0015). Sin embargo, el registro se almacena actualmente bajo el único identificador sample_code transmitido en la petición. Debe evaluarse si resulta conveniente segregar estos informes compuestos en registros independientes por muestra.

⛔ Restricciones temporales de validación: agotamiento de créditos de IA

Las canalizaciones de SEM, FESEM, TEM, ICP-OES y EA interactúan con modelos de Gemini. Su verificación se encuentra temporalmente en suspenso debido al agotamiento del saldo de la cuenta:

HTTP 429 - "Your prepayment credits are depleted.
            Please go to AI Studio to manage your project and billing."

Esta contingencia no se soluciona de forma pasiva. Conviene catalogar con precisión los tres tipos de error HTTP 429 experimentados durante el desarrollo:

Mensaje de error Tipología Resolución
The service is receiving too many requests from you Límite de frecuencia por minuto Se restablece automáticamente en segundos
You exceeded your current quota Límite de cuota del plan Depende del ciclo de facturación
Your prepayment credits are depleted Saldo prepagado consumido Requiere recarga de fondos en la cuenta

Estado verificado de estas 5 técnicas previo al consumo de saldo:

  • SEM / FESEM / TEM: Los tres flujos completaron su ciclo integral de almacenamiento (inserción en base de datos con extracción fidedigna de metadatos de Hitachi, JEOL y codificación en nombre de fichero) a lo largo de tres ejecuciones consecutivas. La etapa determinista está validada; la restricción afecta exclusivamente a la generación descriptiva de morfología mediante visión artificial.
  • ICP-OES: Contrastado con éxito frente a un informe PDF real en una ocasión.
  • EA: Es la única técnica cuya extracción no ha podido comprobarse tras la corrección del parámetro mimeType. Constituye la prioridad de validación una vez se disponga de saldo.

Protocolo de reactivación tras la recarga de fondos

python src/verify_webhook_pipeline.py          # ejecución de los 18 casos de prueba

Si la extracción refleja con exactitud el contenido de los informes a lo largo de diversos ensayos, se podrá reconectar la salida FALSE del nodo If - Needs Human Approval? a DB Update para habilitar nuevamente la ingesta desatendida (L4). Hasta entonces, permanecerá desacoplada deliberadamente.

  • En el apartado 4 de la Parte 2 se mencionan expresiones regulares de códigos de muestra (RS\d+, IEF-\d+, RSMix\d+, LP\d+). Parecen corresponder a prefijos de muestras sin seudonimizar del histórico del laboratorio; se han conservado literalmente al tratarse de patrones de código.
